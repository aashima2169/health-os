# Health OS

## Core Product Belief

Health OS is not a symptom tracker.

Health OS is an investigation engine.

The value is not collecting more data.

The value is helping users discover why chronic symptoms happen by reasoning across months of structured data.

Every feature should answer one question:

"How does this help the user understand why something is happening?"

AI should generate hypotheses, not diagnoses.

Every insight is probabilistic and should clearly communicate uncertainty.

## Decision Framework

When implementing any feature, prioritize in this order:

1. Does this help explain "why" a symptom or flare occurred?
2. Does this reduce logging effort for the user?
3. Does this improve longitudinal reasoning?
4. Can this component be reused elsewhere?
5. Is this the simplest implementation?

If a feature collects data but does not improve reasoning, question whether it belongs in the product.

# Health OS - AI Engineering Guide

## Product Vision

Health OS is an AI-powered health investigation platform.

The goal is NOT to diagnose diseases.

The goal is to help users discover longitudinal patterns that contribute to chronic symptoms by combining daily lifestyle data, symptoms, events, weather, blood reports and AI reasoning.

The product focuses on investigation rather than diagnosis.

Users should gradually understand their own body over 3-6 months and ideally no longer require the app once they have identified their personal triggers.

---

# Target Users

Primary users:

- Autoimmune conditions
- IBS / Gut disorders
- Chronic inflammation
- Hormonal disorders
- Fatigue
- Chronic unexplained symptoms

Doctors are secondary users.

The product should eventually assist doctors by presenting structured patient timelines and AI-generated hypotheses.

---

# Product Philosophy

Health OS should never generate certainty.

Instead of saying

"This caused your flare."

Always say

"Possible contributing factor."

or

"Pattern worth investigating."

Everything generated by AI is a hypothesis.

Never present medical advice as fact.

---

# Design Principles

Health OS is intentionally calm.

Avoid dashboards full of charts.

Prefer

- cards
- timelines
- simple summaries
- whitespace

The experience should reduce anxiety.

Avoid using alarming colors unless displaying actual flare severity.

Signals generates hypotheses from:

- events
- flare history
- weather
- humidity
- blood markers
- photos
- period history
- movement
- recovery
- supplements
- meals
- reflections

Signals never diagnoses.

Signals identifies recurring patterns.

# Database

Supabase is the source of truth.

Never change database schema without explicit approval.

Never rename existing tables.

Never delete migrations.

Never hardcode IDs.

---

# AI Reasoning Principles

The model should reason across multiple dimensions.

Never use simplistic rules such as:

"Low sleep causes fatigue."

Instead evaluate combinations such as:

- blood markers
- sleep consistency
- movement load
- weather
- humidity
- menstrual phase
- recovery activities
- supplements
- diet
- stress
- emotional state
- active flare history

Generate competing hypotheses.

Rank them by confidence.

Clearly state missing information.

Avoid hallucinating causal relationships.

## Implementation Philosophy

Health OS should be built in layers.

Layer 1
Data collection

Layer 2
Timeline

Layer 3
Reasoning

Layer 4
Doctor support

Each new feature should strengthen one of these layers.

Avoid building isolated features.

## Data Collection Philosophy

Every question asked to the user must have a clear purpose.

Before adding any field, ask:

1. Does this improve AI reasoning?
2. Can this be inferred from existing data?
3. Is it required only once?
4. Does it increase cognitive load?

If the answer to (1) is no or (2) is yes, do not ask the user.

## User Language

Health OS should speak in the user's language, not the system's language.

Avoid exposing internal concepts such as:

- Specialist Board
- AI Reasoning Engine
- Consolidator Agent
- Hypothesis Engine
- Investigation Pipeline

Instead use language such as:

- Health journey
- Patterns over time
- Your health baseline
- Personalized insights
- Possible contributing factors

Users should feel they are understanding their body, not interacting with an AI system.

## Current Architecture

The current multi-agent specialist board is an implementation detail and is subject to change.

New features should not be tightly coupled to the specialist board.

Instead, build reusable modules that can later be consumed by different reasoning engines.

The user-facing product is Signals, not the specialist board.
